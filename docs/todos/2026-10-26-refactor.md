# SetupCase Core

## Disclaimer

> **Important: SetupCase Core is rough scaffolding, not a secured product.**
>
> SetupCase Core is a starting point for getting a basic CakePHP application up and running quickly. It is provided as is, without warranty of any kind, and makes no promise of security or fitness for production.
>
> Features such as login throttling are basic safeguards only. They are not meant to replace the detailed security review, testing and hardening you should do before launching your own project publicly. That work is your responsibility.

## Branches

- **main**: the stable core. New projects start from here.
- **test flight**: a disposable proof branch. It is always rebuilt from zero to prove the setup works from scratch. It is never used for customer work.

## The cycle

1. **Rebuild.** Start locally with no source files. Run the from-scratch build (CakePHP plus the application foundation) and confirm everything works.
2. **Deploy test flight.** Commit the result to the test flight branch and tag the starting point:

   ```
   git tag -f testflight-base
   ```
3. **Live on it.** Over the following weeks, ship small fixes and improvements directly in test flight.
4. **Harvest.** List only what changed since the rebuild:

   ```
   git diff --name-only testflight-base
   ```

   Review each file, then copy the intended changes into main. Never merge the whole branch.
5. **Verify the rebuild reproduces it.** Rebuild test flight from scratch out of the updated main. Every harvested change must reappear. If one does not, it only ever lived in test flight and would be lost; fix main before going on.
6. **Go live again.** Re-tag `testflight-base` and repeat.

## Promoting code from customer projects

Customer work never happens in this repository. When a feature built for a customer should carry forward to future projects:

1. Lift only the small, generic piece of code. Strip out all customer names, data, credentials and business rules.
2. Add it to the application foundation inside test flight.
3. Let it travel to main through the normal harvest (step 4 above).

Before every push, check that the commit contains no client names, secrets, hosting details or customer-specific journeys. Check AGENTS.md as well.

## Login throttling

SetupCase Core slows down password guessing by temporarily blocking repeated failed logins.

- **What is counted:** failed attempts per IP address plus the submitted username (lowercased and trimmed). The username counts whether or not the account exists, so attackers cannot use the block to find out which accounts are real.
- **Limit:** after a set number of failures (default 5) within a time window, further attempts are refused for a cooldown period (default 5 minutes). Both values are configurable.
- **Storage:** attempts are stored server-side (database or cache), never in the session, so clearing cookies does not reset the count.
- **Real IP:** if the app sits behind a proxy or CDN, configure trusted proxies. Otherwise forwarded IP headers can be faked or every request may appear to come from the proxy.
- **Shared networks:** offices behind a single public IP share that IP. Because blocking also depends on the username, one person's mistakes do not lock out colleagues.
- **Scope:** this only defends against brute-force password guessing. It does not protect against vulnerabilities in PHP, frameworks or libraries.
